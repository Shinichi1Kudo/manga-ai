# 支付宝电脑网站支付切换设计

## 目标

将现有基于 `alipay.trade.precreate` 的站内二维码支付改为支付宝电脑网站支付。用户购买会员或充值积分时，浏览器跳转到支付宝官方收银台，可扫码或登录支付宝完成付款。

会员套餐保持一次性购买，到期自动结束。本次不接入签约、自动扣款、自动续费或解约能力。

## 已确认决策

1. 支付产品使用支付宝电脑网站支付 `alipay.trade.page.pay`。
2. Java SDK 使用 `pageExecute(request, "POST")` 生成 HTML 表单。
3. 前端在当前窗口提交支付宝表单，不打开新窗口。
4. 网站域名统一使用 `www.yzmovie.cn`。
5. 支付同步返回地址为 `https://www.yzmovie.cn/membership/payment/result/`。
6. 支付异步通知地址为 `https://www.yzmovie.cn/api/v1/payments/alipay/notify`。
7. 支付结果只以异步通知或服务端交易查询为准，不信任同步返回参数。
8. 本次不改变现有会员积分发放规则。

## 方案比较

### 方案 A：现有 JSON API 返回支付表单

后端创建本地订单并返回 SDK 生成的 `paymentHtml`，会员页将表单写入临时容器后自动提交。

优点：复用现有会员和充值下单接口，改动集中，错误提示仍由当前页面处理。

缺点：前端需要处理服务端生成的 HTML。该 HTML 仅来自支付宝 Java SDK，不接受用户输入，并通过已登录的同源接口返回。

### 方案 B：Django 中转页直接返回 HTML

会员页提交普通表单到 Django，Django 调用 Java 后端后直接返回支付宝 HTML。

优点：浏览器跳转路径传统，不需要前端注入 HTML。

缺点：需要为会员和充值增加中转接口，与现有 JSON API 形成两套入口。

### 方案 C：生成 GET 支付 URL

Java SDK 使用 GET 模式生成支付宝 URL，前端直接跳转。

优点：前端实现简单。

缺点：支付参数暴露在 URL，且支付宝文档建议电脑网站支付优先使用 POST 表单。

最终选择方案 A。

## 支付流程

```text
用户点击购买
  -> 前端检查登录状态
  -> Django 代理下单请求并携带用户 Token
  -> Java 后端生成唯一商户订单号和订单快照
  -> Java SDK pageExecute 生成支付宝 POST 表单
  -> 后端保存 CREATED 订单并返回 paymentHtml
  -> 前端渲染并提交表单
  -> 浏览器跳转支付宝官方收银台
  -> 用户完成付款
  -> 支付宝异步通知后端并回跳支付结果页
  -> 后端验签、校验订单/金额/AppID/商户号并幂等结算
  -> 结果页调用交易查询接口兜底
  -> 显示支付成功、处理中或失败状态
```

## 后端设计

### 支付客户端

支付宝客户端由预下单切换为页面支付：

1. 使用 `AlipayTradePagePayRequest` 和 `AlipayTradePagePayModel`。
2. 必填 `out_trade_no`、`total_amount`、`subject`。
3. `product_code` 固定为 `FAST_INSTANT_TRADE_PAY`。
4. 设置固定的 `notify_url` 和 `return_url`。
5. 使用 `pageExecute(request, "POST")`，返回 `response.getBody()`。
6. 保留 `alipay.trade.query`、通知验签和现有结算逻辑。

### API 响应

会员和充值下单接口继续返回 JSON，订单响应中的二维码字段改为 `paymentHtml`。支付表单不写入数据库，数据库只保存订单快照和支付状态。

状态查询接口不返回支付表单，避免重复暴露和存储大段 HTML。

### 配置

在支付宝配置中增加 `return-url`，并将默认回调域名修正为 `.cn`。应用私钥和支付宝公钥继续只通过环境变量注入，不写入代码、配置示例或日志。

## 前端设计

### 会员页

1. 移除站内二维码弹窗、二维码依赖和轮询定时器。
2. 充值按钮改为“前往支付宝支付”。
3. 会员按钮中的“订阅”统一改为“一次性购买”。
4. 套餐说明改为“单次支付，到期自动结束”，不再展示自动续订或可取消文案。
5. 下单成功后校验 `paymentHtml` 中存在表单，将其放入临时全屏容器并调用 `form.submit()`。
6. 下单失败时恢复按钮状态并展示明确错误，不进行页面跳转。

### 支付结果页

新增 `/membership/payment/result/` 页面。页面读取支付宝同步返回的 `out_trade_no` 仅作为查询键，然后调用本站订单同步接口。

页面状态：

| 状态 | 展示与行为 |
| --- | --- |
| 查询中 | 显示正在确认支付结果 |
| 已支付 | 显示支付成功，并提供返回会员页入口 |
| 待支付 | 显示尚未确认到账，可重新查询或返回会员页 |
| 已关闭/失败 | 显示订单未完成，不自动创建新订单 |
| 未登录 | 跳转登录页，登录后可重新进入结果页 |

同步返回中的金额、交易状态等字段不直接用于开通会员或增加积分。

## 结算与安全

现有结算规则继续生效：

1. 只接受 `TRADE_SUCCESS` 或 `TRADE_FINISHED`。
2. 异步通知必须先使用支付宝公钥验签。
3. 校验 `out_trade_no`、`total_amount`、`app_id` 和 `seller_id`。
4. 订单状态更新使用条件更新，保证重复通知和重复查询不会重复发放积分。
5. 前台返回结果不可信，支付查询作为异步通知缺失时的兜底。
6. 私钥只存在于后端运行环境，不进入客户端、日志或 Git 仓库。

## 错误处理

1. 支付宝配置不完整时，下单接口返回明确配置错误。
2. SDK 无法生成支付表单时不返回成功响应，也不让前端提交空表单。
3. 支付表单生成后数据库保存失败时不向前端返回表单。
4. 支付返回页查询到“交易不存在”时展示待支付，不误判失败。
5. 回调处理异常返回 `fail`，让支付宝按规则重试。
6. 用户关闭支付宝收银台后可以回到会员页重新发起支付；同一商户订单号不创建第二次成功支付。

## 测试策略

### 后端

1. 支付客户端使用 `pageExecute(..., "POST")`。
2. 页面支付模型包含订单号、金额、标题和 `FAST_INSTANT_TRADE_PAY`。
3. 请求包含 `.cn` 的返回地址和异步通知地址。
4. 会员和充值下单响应返回 `paymentHtml`。
5. 交易查询、通知验签、金额和商户校验、幂等积分入账测试继续通过。

### 前端

1. 会员页不再包含二维码库和二维码弹窗。
2. 会员与充值按钮请求正确接口。
3. 下单成功后提交返回的支付宝表单。
4. 支付结果页使用 `out_trade_no` 调用订单同步接口。
5. 未登录和查询失败状态有明确处理。

### 沙箱验证

1. 使用沙箱网关生成支付宝电脑收银台。
2. 使用沙箱买家账号或沙箱钱包完成付款。
3. 从返回页主动查询订单，确认会员或积分只到账一次。
4. 沙箱验证完成后，生产环境仍需验证公网回调、正式产品权限和真实账号支付。

## 不在本次范围

1. 支付宝自动续费、签约和周期扣款。
2. 退款接口、退款管理页面和对账后台。
3. 手机浏览器专用 `alipay.trade.wap.pay`。
4. 会员积分按月定时发放规则调整。
5. 生产密钥配置和生产环境真实付款。
