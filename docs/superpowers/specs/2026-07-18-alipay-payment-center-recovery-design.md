# 支付宝统一支付中心与待支付订单恢复设计

## 目标

修复支付宝订单码支付在生产环境无法渲染二维码的问题，并将当前一次性支付弹窗升级为可持续恢复的统一支付中心。

用户点击会员套餐或积分充值后，支付中心立即打开并始终保持可见。即使支付宝预下单暂时失败、二维码脚本加载失败、用户关闭面板或页面刷新，已经创建成功的待支付订单也能从头像旁的订单入口重新打开。

本次继续支持支付宝订单码支付 `alipay.trade.precreate` 和电脑网站支付 `alipay.trade.page.pay`，不改变现有会员与积分结算规则。

## 已确认决策

1. 桌面端使用右侧统一支付中心，移动端使用全屏支付中心。
2. 头像旁增加独立订单图标，并用数字角标显示当前用户的待支付订单数。
3. 支付中心包含“当前支付”和“待支付订单”两个页签。
4. 点击扫码支付后，支付中心保持打开并展示创建进度；下单成功后在同一面板切换为二维码状态。
5. 关闭支付中心不撤销订单，用户可通过订单图标重新进入。
6. 二维码渲染失败只属于前端展示错误，不能把真实支付订单标记为 `FAILED` 或 `CLOSED`。
7. 支付宝瞬时网络错误最多自动尝试 3 次，使用短退避；耗尽后保留面板并提供手动重试和官方收银台后备路径。
8. 待支付二维码仍使用支付宝官方 2 小时有效期，过期后由后端先查询再撤销。

## 已确认根因

### 生产静态资源缺失

2026-07-18 检查生产会员页时，HTML 引用了：

```text
/static/vendor/qrcode/qrcode.min.js
```

该地址实际返回 `404 Not Found`，因此浏览器中不存在 `window.QRCode`。当前页面捕获该异常后统一显示“二维码生成失败，请切换支付宝收银台”，强制刷新无法恢复缺失的服务器文件。

### 生产调用参数错误

项目固定使用 `qrcode@1.5.3`。该库浏览器 API 的正确签名是：

```javascript
QRCode.toCanvas(canvas, text, options)
```

生产页面当前使用了：

```javascript
QRCode.toCanvas(text, { canvas })
```

这不是 `qrcode@1.5.3` 支持的 Canvas 参数形式。仓库当前代码中的 `QRCode.toCanvas(canvas, order.qrCode, options)` 才是正确调用。

### 代码与生产部署漂移

当前 Git 分支与远端均停留在提交 `b5e8cb8`，没有日志中提到的预下单重试和 20:49 前端改动。生产环境存在未提交部署变更。实施时必须先将有效的后端重试逻辑按本设计重新纳入 Git，禁止继续直接修改服务器文件。

## 技术方案比较

### 方案 A：修复本地二维码依赖并增加支付链接后备

继续使用仓库内固定版本 `qrcode@1.5.3`，修正调用、补齐静态资源发布和运行时加载检查。若脚本仍不可用，支付中心保留订单并展示“重试渲染”“打开支付宝付款链接”和“切换官方收银台”。

优点：与现有代码一致，改动集中，不新增后端图片生成依赖。

缺点：二维码图片仍依赖前端静态资源，但发布检查与后备入口可以避免订单不可恢复。

### 方案 B：Java 后端生成二维码 PNG

Java 后端引入二维码图片库，根据支付宝 `qr_code` 生成 PNG 或 Data URL，前端只展示图片。

优点：浏览器不再依赖二维码脚本。

缺点：增加后端依赖和二进制响应链路；待支付订单恢复还需要额外图片接口或重复编码。

### 方案 C：运行时加载第三方 CDN

从公共 CDN 加载二维码库。

优点：部署步骤少。

缺点：支付页面依赖第三方网络和供应链，不符合当前固定版本、本地托管策略。

最终选择方案 A。

## 统一支付中心交互

### 常驻入口

已登录用户的头像旁增加独立订单图标按钮，不嵌套进头像菜单或会员徽章。按钮显示待支付订单数量，数量为零时隐藏角标。

点击订单按钮打开支付中心并默认进入：

1. 当前存在正在操作的订单时，显示“当前支付”。
2. 没有当前订单但存在待支付订单时，显示“待支付订单”。
3. 两者都不存在时，显示空状态和“查看会员套餐”入口。

### 桌面与移动端

桌面端支付中心从右侧进入，宽度限制在可扫描二维码且不遮满页面的范围内。移动端使用全屏面板，顶部保留返回按钮和标题，二维码与操作按钮不横向溢出。

侧栏只使用一个表层容器，不在弹窗内继续嵌套卡片式弹窗。

### 支付方式选择

点击套餐或充值按钮后立即打开支付中心并展示商品、服务端价格和两种支付方式。

用户选择扫码支付后：

1. 面板进入 `CREATING`，支付方式按钮锁定并显示创建进度。
2. 请求期间不隐藏面板，也不出现页面无反馈空档。
3. 后端返回 QR 订单后，面板原地进入 `QR_READY`。
4. 后端错误时进入 `CREATE_ERROR`，保留商品与金额并允许重新尝试或改用收银台。

选择官方收银台后，面板进入 `PAGE_REDIRECTING`。只有通过现有支付宝域名、HTTPS、POST 表单白名单校验后才提交表单。

### 二维码展示失败

二维码绘制异常时进入 `QR_RENDER_ERROR`，但后端订单继续保持 `CREATED`。面板必须继续显示：

1. 商品名称、服务端金额和订单号。
2. 二维码有效期倒计时。
3. “重试渲染”。
4. “打开支付宝付款链接”。
5. “切换官方收银台”。
6. “我已完成支付，立即查询”。

前端不得把 `currentQrOrder.status` 改成 `FAILED`。支付状态与渲染状态使用两个独立字段维护。

### 关闭与恢复

用户关闭支付中心时停止页面轮询和倒计时定时器，但不修改后端订单。重新打开订单时，根据后端返回的 `status` 和 `expiresAt` 恢复倒计时并立即主动查询一次。

页面切换到后台时暂停轮询，重新可见时立即同步一次并恢复每 5 秒轮询。

## 前端状态模型

支付中心界面状态与订单业务状态分离：

| 界面状态 | 含义 | 后端订单状态 |
| --- | --- | --- |
| `IDLE` | 未选择商品 | 无要求 |
| `CHOOSING` | 选择支付方式 | 尚未创建 |
| `CREATING` | 正在预下单 | 尚未创建或请求处理中 |
| `CREATE_ERROR` | 预下单明确失败 | 无待支付订单 |
| `QR_READY` | 二维码已渲染 | `CREATED` |
| `QR_RENDER_ERROR` | 二维码展示失败 | 仍为 `CREATED` |
| `QUERYING` | 正在主动查询 | `CREATED` |
| `PAID` | 支付成功且权益到账 | `PAID` |
| `EXPIRED` | 查询并撤销后关闭 | `CLOSED` |
| `PAGE_REDIRECTING` | 即将提交收银台表单 | `CREATED` |

任何浏览器异常都不得直接把订单业务状态从 `CREATED` 改成失败或关闭。

## 后端 API 设计

### 待支付订单列表

新增：

```http
GET /v1/payments/orders/pending
```

只返回当前登录用户状态为 `CREATED` 且尚未到本地失效时间的订单，按创建时间倒序，默认最多 20 条。响应字段：

```json
{
  "orderNo": "PAY...",
  "orderType": "MEMBERSHIP|RECHARGE",
  "productName": "积分充值¥50",
  "amountCents": 5000,
  "paymentMethod": "QR|PAGE",
  "status": "CREATED",
  "expiresAt": "ISO-8601",
  "createdAt": "ISO-8601"
}
```

列表不返回支付宝表单。二维码原始字符串也不在列表批量返回。

### 恢复待支付订单

新增：

```http
POST /v1/payments/orders/{orderNo}/resume
```

处理规则：

1. 校验登录用户和订单归属。
2. 只允许恢复 `CREATED` 订单。
3. 先调用支付宝查询接口确认最新状态。
4. 已支付则执行现有幂等结算并返回 `PAID`。
5. 已关闭则同步本地 `CLOSED`。
6. QR 订单未过期时返回数据库中已保存的 `qrCode` 和 `expiresAt`。
7. PAGE 订单仍待支付时，使用相同订单快照重新生成安全 POST 表单，不改变金额或权益。
8. QR 订单到期时执行最后查询与撤销，确认后返回 `CLOSED`，不返回旧二维码。

### 主动查询

复用：

```http
POST /v1/payments/orders/{orderNo}/sync
```

前端轮询只使用本站接口。前台二维码链接或支付宝客户端页面不能作为支付成功依据。

## 支付宝预下单重试

只对明确的瞬时网络故障进行自动重试，包括网关 `502/503/504`、连接重置和网络超时。业务错误如 `ACQ.ACCESS_FORBIDDEN`、参数错误或签名错误不重试。

重试规则：

1. 最多 3 次调用，金额、商品和权益始终使用同一份服务端订单快照。
2. 瞬时异常后的下一次预下单使用新的 `out_trade_no`，不复用状态不明确的支付宝商户订单号；只把最终成功返回二维码的订单号写入 `payment_order`。
3. 两次重试前分别进行约 1 秒、2 秒的短退避，并加入小幅随机抖动。
4. 每次日志只记录订单号、尝试次数、网关错误码和可公开诊断信息，不记录私钥、完整签名或二维码字符串。
5. 重试耗尽后返回用户可读错误，支付中心保持打开。
6. 用户手动重试继续创建新的商户订单号，避免把状态不明确的失败请求冒充成功。
7. 沙箱长时间不可用时不继续占用请求线程；用户可切换电脑网站支付。

## 数据与并发

现有 `payment_order` 已保存 `payment_method`、`qrcode` 和 `expires_at`，恢复功能不需要新表。

必要索引继续使用 `(status, payment_method, expires_at)`。待支付列表增加用户条件后，需要确认现有索引执行计划；如扫描成本不合理，新增 `(user_id, status, created_at)` 索引。

结算继续只允许条件更新 `CREATED -> PAID`。恢复、异步回调、主动查询和过期撤销并发时，只有第一个成功的条件更新可以发放积分或会员权益。

## 静态资源发布

发布前必须执行 Django 静态资源收集，并由 Nginx 指向 `STATIC_ROOT`：

```text
python3 manage.py collectstatic --noinput
```

发布门禁必须验证：

1. Django static finder 能找到 `vendor/qrcode/qrcode.min.js`。
2. 生产 URL `/static/vendor/qrcode/qrcode.min.js` 返回 `200`，且响应不是 HTML 404 页面。
3. 生产会员页加载后 `window.QRCode.toCanvas` 存在。
4. 浏览器使用测试 QR 字符串调用 `QRCode.toCanvas(canvas, text, options)` 后，Canvas 非空。
5. 静态资源 URL 增加固定版本参数或使用哈希文件名，避免旧 HTML 与新脚本缓存错配。

禁止在生产服务器直接编辑模板或静态文件。所有修复必须提交 Git，再通过统一发布流程部署。

## 错误处理与安全

1. 预下单失败不创建可恢复的待支付订单，界面保留商品信息供用户重新尝试。
2. 预下单成功但二维码渲染失败时，订单已经存在，必须保留并允许恢复。
3. `qrCode` 只通过已登录且校验订单归属的接口返回，并在作为可点击链接前校验为 `https://qr.alipay.com/` 域名。
4. 订单金额、积分和会员权益继续只读取服务端产品目录与订单快照。
5. 支付结果只接受支付宝验签通知或服务端查询。
6. 收银台 HTML 继续使用 DOM 解析、HTTPS 域名白名单和安全 POST 表单重建，不直接写入页面。
7. 前端错误日志只记录错误类型和订单号，不输出完整支付宝二维码字符串。
8. 私钥、支付宝公钥配置和 Git Token 不进入模板、浏览器日志或 Git 仓库。

## 测试策略

### 前端自动化

1. 支付方式选择后侧栏保持可见并进入 `CREATING`。
2. QR 下单成功后原地切换 `QR_READY`。
3. `QRCode.toCanvas` 使用 `canvas, text, options` 参数顺序。
4. 静态脚本缺失时进入 `QR_RENDER_ERROR`，订单状态仍为 `CREATED`。
5. 渲染失败时订单号、倒计时、重试、付款链接和收银台入口仍可用。
6. 关闭再打开支付中心可从待支付列表恢复订单。
7. 页面隐藏、成功、关闭和过期时轮询正确停止。
8. 支付成功重新请求用户信息，刷新积分、会员徽章和待支付角标。
9. 桌面和移动端支付中心不溢出、不遮挡关键操作。

### 后端自动化

1. 待支付列表只返回当前用户 `CREATED` 订单并限制数量。
2. 恢复接口拒绝越权订单和非待支付状态。
3. QR 恢复返回原二维码，不重新创建支付宝交易。
4. PAGE 恢复使用订单快照重新生成表单。
5. 恢复前查询到支付成功时只结算一次。
6. 到期 QR 订单先查询再撤销。
7. 瞬时网关错误最多重试 3 次，业务错误不重试。
8. 回调、恢复查询和撤销并发时不重复发放权益。

### 发布与浏览器验收

1. 完整运行 Maven 和 Django 测试。
2. 运行静态资源收集并检查二维码文件存在。
3. 在 1280x720 和 390x844 验收订单入口、侧栏、全屏移动布局、待支付列表和二维码。
4. 检查浏览器控制台与网络请求，二维码脚本不得为 404。
5. 沙箱分别验证首次成功、一次 504 后成功、重试耗尽后手动重试、关闭后恢复和支付成功入账。

## 不在本次范围

1. 退款、退款审核和对账后台。
2. 支付宝自动续费、签约和周期扣款。
3. 独立的完整订单历史页面。
4. 修改现有会员价格、积分比例或权益规则。
5. 使用第三方二维码 CDN 或在线二维码生成服务。
