# 首屏渲染与扫码支付可靠性改造设计

日期：2026-08-01

目标分支：`dev_20260629_pay`

状态：已确认采用方案 1，待书面设计复核后实施

## 1. 背景与目标

本次改造同时解决三个用户可见问题：

1. 网站首次打开时，页面会短暂出现未排版文本挤在一起，随后才恢复正常布局。
2. 支付宝扫码支付页面需要显示真实的二维码有效期倒计时，同时继续保留订单号，正常状态下不恢复“立即查询”“正在查询支付状态”等操作或提示。
3. 用户完成一笔 50 元充值后再次创建 100 元充值，支付宝扫码提示“订单不存在”；系统不应向用户展示未经支付宝确认可用的二维码。

改造保持现有视觉样式、价格规则、积分到账规则和订单幂等逻辑不变。正常扫码页最终只展示商品与金额、二维码、有效期倒计时、订单号；异常时才提供安全提示或官方收银台兜底入口。

## 2. 已确认根因

### 2.1 首屏样式闪烁

主页面在浏览器中运行 `https://cdn.tailwindcss.com` 后才动态生成 Tailwind 样式。网络较慢或冷缓存时，HTML 会先按无样式状态绘制，因此出现文本堆叠；Google Fonts 等外部字体资源会进一步放大文字尺寸和布局变化。

### 2.2 二维码倒计时被模板隐藏

前端已有基于服务端 `expiresAt` 的倒计时、到期停止计时和最终状态同步逻辑，但模板给倒计时元素增加了 `hidden`，所以用户看不到有效期。

### 2.3 支付宝订单不存在

本地订单 `PAY202608011856573242653` 已成功保存并生成二维码，但随后使用同一订单号调用支付宝查询接口，两次均返回 `ACQ.TRADE_NOT_EXIST`。该订单未过期，本地仍为 `CREATED`，说明“本地有订单/二维码”并不能证明支付宝侧已形成可支付交易。

当前预创建请求还发送了现行官方接口文档未列出的 `qr_code_timeout_express` 参数，且系统没有校验支付宝预创建响应中的订单号，也没有在二维码展示前通过查询接口确认支付宝侧交易状态。

## 3. 方案设计

### 3.1 首屏改为本地静态样式

- 增加 Tailwind 本地构建配置，从模板和脚本中扫描实际使用的类，产出版本化的 `frontend/static/css/site.css`。
- 在 `<head>` 内直接加载本地 CSS，并移除 `cdn.tailwindcss.com` 运行时脚本。浏览器第一次绘制正文前即可获得完整布局样式。
- 保持现有 Tailwind 主题配置和页面外观一致，不在本次改造中重新设计页面。
- 将关键字体资源放入本地静态目录并只预加载首屏需要的字体文件；同时设置尺寸接近的系统字体回退，避免外部字体请求导致布局偏移。
- 将 Lucide 图标依赖改为本地静态资源并延后到 DOM 可用后初始化。图标加载失败不得影响页面主体布局。
- 静态资源沿用现有版本参数或内容指纹，部署后避免旧 HTML 命中新旧不一致的缓存。

验收标准：在冷缓存和受限网速下，首屏初次绘制已经具有正确布局，不再短暂显示无样式文本堆叠；页面不再请求 Tailwind CDN，主要布局也不依赖外部字体或图标请求成功。

### 3.2 支付宝预创建结果校验

后端把“支付宝返回了二维码”和“该二维码已确认可以展示”拆成两个阶段：

1. 使用唯一的 `out_trade_no` 调用 `alipay.trade.precreate`。
2. 不再发送现行接口未定义的 `qr_code_timeout_express` 参数；二维码有效期按订单码支付固定两小时在服务端计算。
3. 读取并校验支付宝响应中的 `out_trade_no`。为空或与请求订单号不一致时视为失败，不保存、不展示二维码。
4. 预创建成功后等待可配置的短暂传播时间（默认 5 秒），使用相同 `out_trade_no` 调用 `alipay.trade.query`。
5. 仅在查询结果为 `WAIT_BUYER_PAY` 时保存并返回二维码；若已是支付成功状态，则直接走现有幂等结算流程，不再显示二维码。
6. 若首次查询为 `ACQ.TRADE_NOT_EXIST`，在有限窗口内再查询两次，每次间隔 2 秒，以容忍支付宝侧短暂传播延迟。
7. 若有限查询后仍确认交易不存在，关闭该本地未支付订单，生成一个新的订单号并重新执行一次预创建和验证。自动替换最多一次，禁止无限循环。
8. 若替换订单仍不存在，不向前端返回二维码；返回明确、安全的失败状态，并允许用户改用已有的支付宝官方收银台。
9. 网络错误、系统错误或结果不明确时，不自动生成替换订单，因为原订单可能已经可支付；系统保留原订单待后续查询，前端不展示未经确认的二维码，避免重复支付。
10. `TRADE_CLOSED` 等明确终态继续复用现有订单状态机处理。

二维码只在验证通过后持久化并暴露给前端。这样即使支付宝返回异常内容，用户也不会扫到已知无效的付款码。

### 3.3 倒计时与支付页展示

- 移除倒计时元素的 `hidden`，复用现有基于服务端 `expiresAt` 的倒计时，不再新增一套本地估算计时器。
- 正常格式为 `二维码有效期 01:59:59`；刷新页面后仍以服务端到期时间为准，不会重新从两小时开始。
- 倒计时归零时停止计时，触发一次最终状态同步，并显示“正在确认订单最终状态，请勿重复支付”。确认过期后二维码不可继续作为有效付款入口。
- 已支付、已关闭等终态使用对应终态文案，不继续倒数。
- 正常二维码页面保留订单号；继续隐藏“立即查询”按钮、常驻“正在查询支付状态”提示和正常状态下的切换按钮。
- 只有二维码验证失败时才显示错误说明和“切换官方收银台”兜底入口，避免正常界面出现额外操作。

### 3.4 日志与安全

- 记录订单号、支付宝响应码/子码、验证次数、替换订单关系和可用的请求追踪标识。
- 不记录完整二维码内容、密钥、签名、用户凭证或支付链接；如需关联二维码，仅记录不可逆哈希指纹。
- 保留现有订单锁与幂等结算约束，验证阶段发现已支付时只能结算一次。
- 不手工修改本次已出现问题的 100 元订单。它继续由现有查询/过期流程收敛，避免对不确定支付状态做破坏性处理。

## 4. 接口与状态约定

后端支付准备接口应区分以下结果：

- `QR_READY`：支付宝查询确认 `WAIT_BUYER_PAY`，包含二维码、订单号和服务端 `expiresAt`。
- `PAID`：验证期间已支付并完成幂等结算，前端进入成功流程。
- `QR_UNAVAILABLE`：明确无法获得有效二维码，可提示用户重试或切换官方收银台，不包含二维码。
- `PAYMENT_UNKNOWN`：支付状态不明确，提示用户不要重复支付并稍后查询，不自动创建新订单，不包含二维码。

如现有 API 已有等价状态字段，实施时优先扩展现有响应而不是另建重复接口。前端必须以状态字段决定是否渲染二维码，不能仅凭二维码字符串非空判断。

## 5. 测试策略

实现遵循先失败测试、再最小修复的顺序。

### 5.1 前端测试

- 支付模板中二维码倒计时可见，订单号保留，查询按钮和常驻查询状态仍隐藏。
- 倒计时以服务端 `expiresAt` 计算，刷新不重置；到期只触发一次最终同步。
- `QR_UNAVAILABLE` 和 `PAYMENT_UNKNOWN` 不渲染二维码，并分别展示正确的安全提示。
- 基础模板引用本地 `site.css`，不再引用 `cdn.tailwindcss.com`。
- 构建产物包含首屏实际使用的关键样式；冷缓存页面渲染测试不出现无样式正文。

### 5.2 后端测试

- 预创建请求不发送 `qr_code_timeout_express`。
- 支付宝响应订单号为空或不一致时拒绝二维码。
- `WAIT_BUYER_PAY` 验证通过后才保存并返回二维码。
- 验证期间已支付时只执行一次结算。
- `TRADE_NOT_EXIST` 按上限查询，并且最多创建一个替换订单。
- 替换订单仍不存在时返回 `QR_UNAVAILABLE`，不暴露二维码。
- 网络错误或未知状态返回 `PAYMENT_UNKNOWN`，不得创建替换订单。
- 多请求并发时不产生重复订单替换或重复积分到账。

### 5.3 回归与线上验证

- 运行前端完整测试集和后端支付相关测试，并在可接受时运行后端完整测试。
- 构建生产前端与后端，确认静态资源引用、健康检查和服务日志正常。
- 使用冷缓存及限速方式访问公网首页，确认首屏无样式闪烁且不请求 Tailwind CDN。
- 在不发起真实扣款的前提下验证支付准备接口、二维码倒计时和异常分支。真实支付验收由用户主动扫码完成，系统不会自动创建或支付测试订单。
