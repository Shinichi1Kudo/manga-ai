# 支付宝二维码安全刷新设计

## 背景

当前订单码支付会把支付宝 `alipay.trade.precreate` 返回的 `qr_code` 保存到
`payment_order.qrcode`。用户从“待支付订单”继续支付时，后端优先返回这条已保存的
二维码。

这能恢复正常的待支付订单，但不能处理以下情况：

- 二维码已被错误的支付宝客户端扫描，支付宝侧不再接受重复扫描。
- 支付宝侧二维码不可用，但本地订单仍处于 `CREATED` 且尚未到两小时。
- 待支付订单没有保存到二维码，前端只能进入没有可见二维码的恢复状态。

“重新渲染二维码”只会重画同一个 `qr_code`，不能解决支付宝侧二维码已经失效的问题。

## 目标

1. 用户可以为一笔仍待支付的扫码订单安全生成全新的支付宝订单码。
2. 刷新前必须确认旧订单没有支付，禁止同时保留两个可支付订单。
3. 从待支付订单继续支付时，不再出现空白二维码区域；无法恢复时提供明确的刷新入口。
4. 支付中心在查询、撤销和重新下单期间始终保持打开。
5. 已支付、状态不确定和并发请求不能造成重复扣款或重复发放权益。

## 方案比较

### 方案一：只重新渲染原二维码

只清空 Canvas 并使用原 `qr_code` 再次绘制。实现简单，但支付宝侧失效的二维码仍然
失效，只适合修复前端渲染故障。

### 方案二：不关闭旧订单，直接创建新订单

能够快速得到新二维码，但旧二维码仍可能完成支付，存在重复付款和重复权益结算风险，
不可采用。

### 方案三：安全替换旧订单

先查询支付宝状态，只有确认旧订单未支付且已关闭后，才创建继承原商品信息的新订单。
这是本次采用的方案。

## 后端设计

### API

新增：

```text
POST /v1/payments/orders/{orderNo}/refresh-qr
```

请求不接收金额、产品或积分参数。新订单的商品、金额、积分和会员权益全部复制自服务端
保存的旧订单。响应继续使用 `PaymentOrderCreateResponse`，成功时返回新订单号、
`qrCode`、`expiresAt` 和 `paymentReady`。

Django 增加同路径代理：

```text
POST /api/payments/orders/{orderNo}/refresh-qr/
```

### 状态流转

接口在旧订单号对应的订单操作锁内执行，并校验登录用户、订单归属、`CREATED` 状态及
`QR` 支付方式。

1. 调用 `alipay.trade.query` 查询旧订单。
2. 若支付宝返回支付成功：按现有主动查询结算逻辑将旧订单更新为 `PAID`，返回已支付
   结果，不创建新订单。
3. 若返回 `WAIT_BUYER_PAY`：调用 `alipay.trade.cancel`。只有撤销结果明确为 `close`
   或 `refund`，才把旧订单从 `CREATED` 更新为 `CLOSED`。
4. 若返回 `TRADE_CLOSED` 或明确不存在：条件更新旧订单为 `CLOSED`。
5. 若查询失败、响应未知或撤销要求重试：保留旧订单，不创建新订单，返回“状态暂不
   确定，请勿重复支付”。
6. 旧订单确认关闭后，复制服务端商品快照生成新的 `QR` 订单，使用新的商户订单号和
   两小时有效期，并执行现有预下单重试与持久化流程。

旧订单的操作锁和 `CREATED -> CLOSED/PAID` 条件更新保证同一 JVM 内的并发刷新只会有
一个请求进入创建新订单阶段。后续重复请求看到旧订单已关闭后直接拒绝，不会再次创建。

### 新订单复制规则

复制以下服务端字段：

- 用户、订单类型、产品编码和产品名称
- 金额、基础积分、赠送积分和总积分
- 会员等级、周期和月数
- 当前支付宝应用及商户身份

重新生成以下字段：

- 商户订单号
- 状态、二维码、有效期和创建/更新时间
- 支付宝交易号、通知及结算相关字段

## 前端设计

### 操作入口

二维码操作区新增“刷新二维码”按钮，使用旋转图标，与现有“重试二维码”区分：

- “重试二维码”：只重新绘制当前二维码，处理 Canvas 或静态资源故障。
- “刷新二维码”：安全关闭旧支付宝订单并创建一笔新订单。

二维码正常显示、二维码待生成或二维码显示失败时，都可以看到“刷新二维码”。点击后
先确认“刷新后旧二维码将失效”，确认后调用刷新接口。

### 交互状态

刷新过程中：

- 支付中心不关闭。
- 显示“正在刷新支付宝二维码”。
- 禁用刷新、查询、切换收银台和待支付恢复操作。
- 忽略重复点击和旧请求返回。

刷新成功后，当前订单切换为后端返回的新订单，清除旧 Canvas，绘制新二维码并重新启动
五秒轮询和倒计时，同时刷新待支付订单数量。

若后端发现旧订单已支付，沿用支付成功流程刷新积分、会员徽章及用户信息。若状态不确定，
保留旧订单号和操作面板，提示不要重复付款。

### 待支付订单恢复

“继续支付”仍先调用 `resume`。响应存在可信 `qrCode` 时立即绘制；响应缺少二维码或
`paymentReady=false` 时显示“二维码暂不可用”，隐藏空 Canvas，并展示“刷新二维码”
按钮。用户无需关闭弹窗或重新选择商品。

## 错误与安全边界

- 不接受前端提供的新订单金额、积分或会员参数。
- 不在日志中记录二维码内容、签名、密钥或支付宝完整响应。
- 状态未知时不撤销、不关闭、不创建新订单。
- 已支付订单只允许进入既有幂等结算流程。
- 前端不以本地倒计时直接判定支付宝交易关闭，最终状态来自后端查询。
- 刷新失败不会清空待支付订单，用户仍可查询旧订单最终状态。

## 测试范围

### 后端

- 非本人、非扫码、非 `CREATED` 订单拒绝刷新。
- 已支付旧单结算且不创建新订单。
- `WAIT_BUYER_PAY` 撤销成功后创建完整的新扫码订单。
- `TRADE_CLOSED` 和明确不存在时创建新订单。
- 查询异常、撤销失败及 `retry_flag=Y` 时不创建新订单。
- 并发或重复刷新不创建第二个替代订单。
- 新订单继承服务端金额、积分和会员权益，使用新订单号及新有效期。

### 前端

- 刷新请求使用 CSRF 且不携带金额或商品数据。
- 刷新期间面板保持打开并阻止并发操作。
- 成功响应替换当前订单并绘制新二维码。
- 已支付响应进入成功流程。
- 状态不确定时保留旧订单和可查询操作。
- 待支付恢复缺少二维码时不显示空 Canvas，并显示刷新入口。

### 浏览器

- 桌面端和 390x844 移动端检查按钮、确认、加载、成功及失败状态。
- 验证待支付订单继续支付后能显示二维码，缺失时能原地生成新二维码。
- 验证新二维码图像非空、订单号变化、旧订单从待支付列表消失。

## 非目标

- 不改变支付宝沙箱与生产环境配置。
- 不自动刷新二维码，刷新必须由用户主动触发。
- 不允许未关闭旧订单时并存新的可支付订单。
- 不修改会员定价、积分规则或支付成功结算规则。
